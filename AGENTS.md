## What Lovable manages

Rules outside this block are the project's own. Change the pieces below in
Lovable, not by hand. With the [Lovable MCP](https://mcp.lovable.dev)
connected, `send_message` asks Lovable to do it; otherwise ask the user to
use the editor.

- **Database.** Do not add or edit `supabase/migrations/` or `drizzle/`.
  Ask Lovable to change the schema.
- **Generated files.** Do not edit a file whose header says it is automatically
  generated.
- **AI gateway.** Keep model calls on Lovable's gateway, and keep
  `LOVABLE_API_KEY` out of browser code.
- **Connectors.** Lovable provides native connectors. `list_connectors` shows
  which are enabled; `add_connector` only returns the dashboard link. When a
  connector is enabled, calls go through the connector gateway and need
  `LOVABLE_API_KEY`. When Lovable does not provide one, users can bring their
  own key and store it in Secrets.
- **Secrets.** Lovable manages them. Do not put secret values in the repo.

## Project rules
- TransactionList offers a flat presentation for the account dashboard while keeping its existing framed presentation for other callers, so dashboard styling does not alter admin views.
- Investment confirmation uses the mounted Face ID attempt in success-only mode; only the video ended event submits the captured order, cancellation discards it, and a submission guard prevents duplicate placement. The animation is presentation, never biometric authentication.
- Sign-in is Google-only through the generated `@/integrations/lovable` module; pages under `src/routes/_authenticated/` are gated client-side (`ssr: false`) and every account server function uses `requireSupabaseAuth` — never reintroduce email or shared-passcode entry.
- Accounts use generated five-digit demo IBANs; the legacy tag and cards table are retained only for compatibility, never exposed or generated by current setup.
- Demo trade placement and settlement are atomic database functions with account/order locks and unique ledger entries; stake is reserved on placement and only pending orders may settle, preventing duplicate payouts.
- Admin functions require authenticated, PIN-unlocked access, a server-verified Google identity and a protected user_roles row; the old public admin URL redirects to the account and never accepts a shared password.
- Leaderboard reads use authenticated PIN-gated server functions and return only masked names, photos and requested demo financial statistics, never raw profile or authentication records.
- P2P transfers use transfer_by_iban with ordered account locks; the transaction trigger remains the only ledger balance adjustment path for transfers and trades.
- Ask AI streams through a session-checked server route with a separate per-user balance/transaction field projection, never the full account loader, so card data cannot enter model context; chat state is component-local.
- Send is a dedicated authenticated route using the existing transfer form; shared account navigation uses validated account view search parameters so browser history and direct links preserve the selected screen.
- Profile photos use owner-folder uploads in private storage, an authenticated PIN-gated path-only update RPC, and signed URLs for account and leaderboard readback; never allow profile-wide updates to change PINs or identifiers.
- Perk action feedback uses an unstyled, transparent Sonner shell and a shared pill notification above bottom navigation; keep the generic toast surface separate so it cannot add a rectangle behind custom feedback.
- Live investment values on the home screen are presentation-only (deterministic per-order wave, then a glide anchored to the server settled_at time so devices agree and finished settlements never replay); balances change only through the database settlement functions.
